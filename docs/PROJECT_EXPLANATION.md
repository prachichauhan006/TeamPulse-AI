# TeamPulse AI — Project Explanation

## 1. Problem and product response

Teams often keep tasks, meeting decisions, documents, and AI-generated plans in disconnected tools. That makes ownership and downstream risk difficult to see, and unrestricted AI automation can create incorrect work before anyone reviews it.

TeamPulse AI combines those workflows in a workspace-isolated application:

- Projects and tasks provide execution structure.
- Dependencies and deterministic rules explain schedule risk.
- Notes and documents become searchable team knowledge.
- AI proposes plans and meeting actions, but people approve every write.
- Membership RBAC and audit records make access and decisions visible.

The result is an “AI operating system for teams” in the literal workflow sense: a shared system of record with assistive AI, not an autonomous agent with unrestricted write access.

## 2. Technology choices

| Layer | Choice | Reason |
|---|---|---|
| Browser | React 18, TypeScript, Vite, Tailwind | Typed component model, fast development, responsive utility styling |
| Server state | TanStack Query | Cache, invalidation, loading/error states, composable API reads |
| Routing | React Router | Protected routes, nested shell, destination redirects |
| API | FastAPI, Pydantic, SQLAlchemy 2 | Typed contracts, dependency injection, modular monolith simplicity |
| Data | PostgreSQL 16, Alembic, pgvector | Relational integrity, versioned schema, vector search |
| Async/rate state | Redis, Celery | Distributed rate-limit state and background embeddings |
| AI | Provider interface + deterministic mock + optional remote implementation | Offline repeatability and replaceable infrastructure |
| Tests | pytest, Ruff, Vitest, Testing Library, Playwright | Unit/API/UI/browser coverage at different boundaries |
| Delivery | Docker Compose, GitHub Actions workflow | Reproducible local topology and automated checks |

A modular monolith keeps the project understandable for an interview and avoids claiming microservice scale that has not been measured. PostgreSQL remains the source of truth; Redis is not used as the system of record.

## 3. Backend organization

### API and dependencies

Routes under `app/api/routes` handle HTTP validation and response codes. Shared dependencies in `app/api/deps.py` resolve the current user and workspace membership, enforce roles, and apply authenticated rate limits. Resource lookups include workspace IDs so an object UUID alone is not sufficient to cross a tenant boundary.

### Models and migrations

The core migration covers users, refresh tokens, workspaces/members, projects, tasks, dependencies, and audit logs. The AI/search migration adds meeting notes, documents, proposals, and embedding chunks. The vector type has a portable test representation while PostgreSQL uses `vector(1536)` and an HNSW cosine index.

Soft-deleted workspace/project/task/note/document records are excluded from active queries. Audit records have no update/delete endpoint.

### Services

- `proposals.py`: pending plan generation, approval transaction, idempotent replay, rejection
- `meeting_actions.py`: extraction proposals and selected-key approval
- `ai_validation.py`: assignee, reference, duplicate, and cycle checks
- `risk.py`: deterministic task/project health with explicit reasons
- `embeddings.py`: chunking, post-commit enqueue, retries, source status, idempotent replacement
- `search.py`: tenant-filtered vector/full-text/SQLite search and duplicate-title suggestions
- `rate_limit.py`: Redis and development/test fallback behavior

## 4. AI trust boundary

The AI provider returns structured data, not executable instructions. The trust sequence is:

1. Treat briefs, notes, documents, and provider output as untrusted input.
2. Parse output with strict Pydantic models; reject extra/invalid fields.
3. Resolve suggested assignees against active members of the same workspace.
4. Validate task keys, dependency references, duplicates, and cycles.
5. Save only a `PENDING` proposal and audit event.
6. Present a clearly labeled preview in the browser.
7. On explicit approval, revalidate current references and write in a transaction.
8. Store created IDs and review metadata; replay approval without duplicate records.

Meeting actions add another human decision: only selected action-item keys are approved. Rejection changes proposal status only. Weekly summaries are read-only and never create a proposal or task.

The mock provider is deterministic and supports plans, meeting extraction, embeddings, and weekly summaries. Its 1536-dimensional hashing-trick embedding is useful for repeatable development, not a claim of state-of-the-art semantics.

## 5. Dependency risk design

Risk is computed from stored facts, not generated by AI:

- `DONE` → `ON_TRACK`
- Explicitly blocked incomplete task → `BLOCKED`
- Incomplete task past its due date → `OVERDUE`
- Blocked/overdue/upcoming unfinished dependency → `AT_RISK` with reasons
- Project health aggregates active task risk into `ON_TRACK`, `AT_RISK`, or `CRITICAL`

This makes the demo explainable. If “Build authentication service” is blocked, “Integrate payment API” shows the exact dependency reason. Self-dependencies and cycles are rejected before a link is committed.

## 6. Knowledge and search flow

Document/note creation commits the source record before embedding is scheduled. A worker:

1. Reloads the same-workspace source and skips deleted content.
2. Splits text into overlapping word chunks.
3. Generates validated 1536-dimensional vectors.
4. Replaces prior chunks atomically for idempotent reruns.
5. Stores safe embedding status/error state.

Search first constrains source IDs and workspace membership, then ranks vectors when available. PostgreSQL can fall back to parameterized ranked full-text search; SQLite tests use `ILIKE`. Tasks are text-search only. Duplicate suggestions use normalized task-title similarity and can be dismissed in the UI without automatic merge/deletion.

## 7. Frontend state and permissions

`AuthProvider` owns access/refresh tokens, current-user restoration, refresh rotation, logout, and session-expired state. `WorkspaceProvider` owns the selected workspace, member list, current role, and persistence of the selection.

TanStack Query keys include workspace IDs so switching workspaces does not intentionally reuse another workspace’s server data. Task list/board views compose the existing task, risk, dependency, project, and member APIs through `useTaskViews`; this avoids changing backend authorization or response contracts.

The UI hides controls that a role cannot use and shows permission explanations where useful. This is not a security substitute: backend dependencies independently enforce every role and workspace check.

## 8. RBAC model

- **OWNER**: full control, including workspace deletion and ownership safeguards
- **ADMIN**: projects, AI plans, members, audit, tasks/notes/documents, workspace rename
- **MEMBER**: tasks/notes/documents and meeting-action workflows; no project/AI-plan/member administration
- **VIEWER**: read-only workspace access

Backend role-grant rules prevent granting above one’s own role and protect the last owner. Project deletion is allowed only when no active tasks remain.

## 9. Testing strategy

### Backend

- Unit tests for security, permissions, dependencies, risk, validation, search, and provider behavior
- API integration tests for authentication, RBAC, tenant isolation, proposal workflows, notes, documents, and summaries
- In-memory SQLite and process-local limiter reset for deterministic isolation
- MockAIProvider only; no paid/external calls

### Frontend unit

Vitest/jsdom and Testing Library cover protected redirect, login/session redirect, workspace switching, AI preview labeling, risk reasons, and role-restricted controls.

### Browser E2E

Five Playwright scenarios use runtime-generated credentials and unique workspaces. They verify registration/login, workspace/project/task creation, blocked-dependency risk, AI preview/approval writes, and tenant isolation. The CI job starts the real Compose topology with mock AI and applies migrations first.

### Important evidence boundary

The build sandbox executed backend and frontend unit/build checks and E2E discovery. It did not execute Docker, PostgreSQL/pgvector, Redis, Celery, or browser E2E. Those remain runtime checks, not passed claims.

## 10. Scaling and production path

The current design is appropriate for a small-team portfolio deployment, but no load test or scale guarantee has been performed. Sensible future work includes:

- Bulk task risk/dependency reads to avoid N+1 browser composition
- Batched/streamed embedding generation for very large sources
- Task embeddings if product evaluation justifies them
- Redis-backed multi-instance deployment and worker monitoring
- HttpOnly refresh-cookie design with CSRF controls
- Short-lived access-token revocation strategy if required
- Backup/restore exercises, observability, security headers, and load testing

These are explicit next steps, not implemented claims.

## 11. Interview-ready summary

“TeamPulse AI is a multi-tenant FastAPI/React application that combines project execution, dependency risk, searchable team knowledge, and approval-gated AI. The key design choice is that AI only creates validated pending proposals; explicit human approval performs transactional writes. I also kept risk deterministic and explainable, and used a provider abstraction plus a deterministic mock so security/workflow tests never depend on a paid model.”
